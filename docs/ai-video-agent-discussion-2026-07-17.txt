有关AI视频Agent导演框架的讨论
问题
先和你说一下我的需求：我在做一些人文社科历史类的科普视频（中长视频），其中有一些文段需要以ai漫剧的形式演绎，我试了一下市面上比较前沿的ai视频工具（即梦、libtv、magiclight、pixverse）各有各的流程，唯一的共同点就是太贵了。但是本地其实都有图片和视频的生成模型，我测了wan2.2 混元 ltx2.0 都是好东西，就是缺一个有导演思维的指挥家（agent/skill），当然我也可以慢慢通过文本手搓人物参考图、然后生成每个分镜的参考图、接着各种生成的视频，耗时不说，我自己也没有足够的导演思维，这就会导致我想要的一组画面组合起来非常奇怪……所以我的理解是这些平台的之所以敢卖那么贵，其实很大一部分原因就是知道这个导演的agent会卡脖子，但是作为资深开发，我总觉得应该会有开源的一套组件去解决这个问题（skill+节点画布+视频推理加速），你看看有没有什么现成的解决方案？
AI回复
你的判断基本成立，但平台真正卖得贵的并不只是一个“会写分镜提示词的导演 Agent”，而是下面这一整套东西：导演规划 + 角色/场景资产管理 + 镜头连续性 + 模型路由 + 自动质检重试 + 可回退的工程状态 + 剪辑合成。截至 2026 年 7 月，开源社区已经有不少组件，但还没有一个项目能同时做到：完全本地、导演能力成熟、可视化节点画布、兼容 Wan/混元/LTX、稳定生产中长视频。不过，已经可以拼出一套相当接近即梦、MagicLight 这类平台的本地系统。

1.1 VideoClaw：最值得直接 fork
它基本就是你描述的产品：
创意/文段 → 剧本 → 角色与场景 → 分镜 → 参考图 → 视频片段 → 后期合成
每个阶段的资产都能查看、修改和重新生成，而且已经支持首帧生视频、首尾帧生视频、参考图生视频，以及 WebUI、项目留存和 OpenClaw Skill。项目采用 MIT 许可证。
问题在于，它目前内置的模型 Provider 主要是 DashScope、火山方舟、Kling、OpenAI、Gemini 等商业接口，Wan 也是通过云端 DashScope 调用，并没有直接接本地 ComfyUI。
但这反而很适合你。 它的导演工作流、资产结构、前后端界面已经有了，你只需要实现：
Plain TextComfyUIImageProviderComfyUIVideoProviderLocalVLMProviderLocalLLMProvider
然后把云端的 generate_image()、generate_video() 替换成提交 ComfyUI workflow JSON 即可。

1.2 creative-skills：本地生成层最好的参考实现
这个项目已经把 Agent Skill 和本地 ComfyUI 真正连起来了：
 Agent 生成 YAML 分镜工程 
 Flux 生成场景锚点图 
 LTX 进行图生视频、首尾帧、续写、多参考帧生成 
 支持不同场景之间的过渡片段 
 FFmpeg 自动合成 
 支持任务恢复、单镜头重跑和质量检查 
 可以把图片服务器和视频服务器分开部署 
它甚至已经考虑到一个常见坑：不能直接拿人物设定图当视频首帧，而应该先生成“人物已经置于具体场景中的镜头锚点”，否则人物设定图的背景和灯光会污染所有镜头。
这套东西非常适合被拆下来，作为 VideoClaw 的本地 ComfyUI Provider。
它的弱点也很明显：目前偏向音乐视频和对白漫剧，主要通过 YAML 和命令行驱动，没有真正成熟的导演工作台。

1.3 AI Storyboard Generator：最容易跑通的本地原型
这个项目是 React 前端，支持：
 OpenAI-Compatible LLM 
 自定义 ComfyUI 图片工作流 
 自定义 ComfyUI 视频工作流 
 配置 workflow 中首帧、尾帧、Prompt、视频输出节点 ID 
 单镜头重生成 
 批量生成 
 FFmpeg 合并 
 项目 ZIP 保存与恢复 
也就是说，它已经完成了最麻烦的“前端分镜卡片 ↔ ComfyUI JSON workflow”连接。
但它的导演能力更像“把文本拆成 N 个画面”，并没有真正处理：
 景别节奏 
 轴线和人物空间关系 
 镜头之间的信息递进 
 场面调度 
 角色出入场 
 视觉母题 
 叙事视角 
适合拿来验证本地生成链路，不适合直接当最终导演系统。

1.4 ViMax：最值得抄“导演脑”的项目
ViMax 的设计很接近真正的导演 Agent：
 长文本 RAG 拆分 
 场景和镜头规划 
 多机位模拟 
 智能选择前序参考图 
 多张候选图并行生成 
 使用 VLM 对人物一致性和构图进行检查 
 自动选择最佳首帧 
 失败重试和状态恢复 
它不是只生成一次，而是有明显的“生成—检查—选择”闭环。
缺点是当前示例仍然主要接 OpenRouter、Google 图像和 Veo 等 API，而且 Web 前端还在 Roadmap 中。
所以它适合作为 VideoClaw 导演层和质检层的参考实现，不适合直接作为底座。

1.5 Story2Board：可以补强分镜图质量
Story2Board 专门解决一个很重要的问题：
保持人物身份一致的同时，不能让所有分镜都变成人物站在画面中央的相似构图。
它通过共享参考 latent 和跨面板 attention 混合，在不训练模型的情况下兼顾人物一致性、背景变化和构图多样性，底层使用 FLUX.1-dev。
它不负责视频，但可以成为你的“分镜参考图生成器”，或者把它的方法移植到 ComfyUI workflow 中。

具体来说：
产品壳和工程状态机：VideoClaw
本地 ComfyUI 调用：creative-skills + AI Storyboard Generator
导演规划与质检逻辑：ViMax
分镜一致性与构图：Story2Board
推理执行：ComfyUI / WanGP / LightX2V
最终装配：FFmpeg 或你自己的剪辑工程
ComfyUI 本身已经原生支持 Wan 2.2、Hunyuan Video、LTX-Video，并提供 API、工作流 JSON、异步队列和局部重执行，适合成为隐藏在产品界面后面的“生成引擎”。
推理加速怎么选
单机、显存有限：WanGP
WanGP 已经支持 Wan、LTX、混元等多个模型，提供量化模型、低显存运行、队列、Headless 模式和 API，很适合快速接进 Agent。
新卡、高吞吐：LightX2V
LightX2V 更像生产推理框架，支持单卡和多卡优化、量化、蒸馏及分布式部署。官方甚至提供了针对特定 Wan 2.2、RTX 5090 和 NVFP4 的极端加速版本，但那种“50 倍”是特定模型、硬件和蒸馏配置，不能理解成所有视频模型都会获得同样收益。
多张异构显卡：优先镜头级并行
考虑到你之前的服务器里还有 Tesla M40 一类老卡，我不建议第一阶段做“一个镜头跨多张卡切分”。
更合理的是：
Plain TextGPU 0：镜头 1GPU 1：镜头 2GPU 2：镜头 3GPU 3：分镜参考图 / VLM 质检
每个 Worker 设置不同的 CUDA_VISIBLE_DEVICES，通过 Redis 队列调度。对于中长视频，镜头之间本来就天然可并行，这通常比异构卡上的张量并行稳定得多。
等换成同型号高端卡，再考虑 LightX2V 或 xDiT 的序列并行、PipeFusion 等多卡推理方案。xDiT 本身就是为大规模 DiT 并行推理设计的。
SageAttention 官方目前主要针对 RTX 3090、4090 优化，其他架构不一定有明显收益，因此不太适合作为 M40 的核心加速方案。
TeaCache 可以用于预览和候选生成，但 ComfyUI 插件曾频繁受到版本更新影响，并且阈值过激时会影响质量，最终出片最好保留一套不使用缓存加速的高质量配置。
人文历史视频还需要额外补一层
通用漫剧 Agent 最容易在历史题材上犯的错误不是“画面不美”，而是：
 不同朝代服饰混用 
 官职、礼仪、建筑错误 
 不存在的道具提前出现 
 同一地点空间结构不断变化 
 为了戏剧效果篡改史实关系 
因此你需要在普通 Character Bible 之外，加一个：
Plain Texthistorical_constraints:  period: 北宋中期  exact_year: 1043  location: 汴京  architecture:    allowed: [木构楼阁, 瓦顶, 坊市街道]    forbidden: [明清硬山顶风格, 现代玻璃, 清代官服]  costume_sources:    - 宋代画像参考    - 出土服饰资料  factual_certainties:    confirmed: [...]    disputed: [...]    dramatized: [...]
导演 Agent 每次生成镜头时，都必须读取这份约束；VLM 质检也要增加“时代错误”和“史料冲突”评分。
最终建议
不要从零开发一个全新的导演 Agent，也不要直接使用 MovieAgent 这种论文项目。
最省时间、最接近产品化的路线是：
fork VideoClaw，增加本地 ComfyUI Provider；借用 creative-skills 的 ComfyUI 调用和多参考帧工作流；把 ViMax 的分镜规划、候选生成、VLM 选优机制移植进去。
节点画布最好分成两层：
 面向创作者的是“场景—镜头—资产—成片”的制作画布； 
 ComfyUI 节点图隐藏在每个生成节点内部。 
不要把完整 ComfyUI 图直接暴露给普通创作者，否则最终仍然只是一个更复杂的本地工作流工具，而不是你真正需要的“AI 导演”。

关于和已有工作管线衔接
你这个上游产线已经不是“给一个粗糙文案，让 Agent 自己发散创作”了，而是已经产出了一个非常像 “导演说明书 / 制片圣经” 的东西。
这意味着我前面给你的那套组合方案，应该从：
“重创意生成型导演 Agent”
微调成：
“强约束执行型导演 Agent / 视觉总控 Agent”
也就是说，系统的重心不再是“帮你想故事和分镜”，而是：
把上游给出的规则结构化
把规则稳定地下发到每个镜头
控制一致性
控制节奏与镜头连续性
把不同模型（Wan / 混元 / LTX）调度起来
自动质检并回炉重做

一句话结论
你的上游已经足够强，不需要一个“会乱发挥”的导演 Agent；你需要的是一个“不会跑偏的执行导演 + 场记 + continuity supervisor + 调度中台”。
所以方案要改成：
弱化：剧本发散、自由分镜、开放式创意生成
强化：结构化约束、镜头状态管理、参考资产管理、模型适配、VLM 质检、镜头连续性控制

为什么要改
你给我的这份示例，已经非常完整了，里面其实包含了四层信息：

1）全局风格约束
也就是你的 Style Lock
这不是普通 prompt，而是全局不可漂移的视觉宪法，包括：
手绘日系插画感
平涂 + 柔和过渡
干净勾线
非写实摄影
留白逻辑
青灰 → 暖金的色温弧线
唯一鲜彩点 = 红笔 / 红叉
固定或极缓推移
各种禁忌项
这层东西应该被系统视为：
Project-level hard constraints（项目级硬约束）
而不是每次让 LLM“重新理解一遍”。

2）全局叙事弧线
也就是你的 故事背景描述
这里面最关键的不是“父亲辅导女儿作业”这个表面剧情，而是：
主题：问题的方向决定情绪走向
情绪弧线：紧张 → 释放
色温弧线：青灰暮色 → 暖金台灯光
空间弧线：留白被挤压 → 留白被归还
节奏弧线：滔滔不绝 → 停顿 → 放软
这其实已经是 导演级调度信息 了。
所以 Agent 不应该重新“想一个更戏剧化的版本”，而是应该把这些弧线编译进每个分镜。

3）角色圣经
你的父亲、女儿描述已经很像 production bible 了：
年龄
长相基调
穿着
动作习惯
情绪表达方式
禁变项
这意味着你不需要一个“角色设计 Agent”，你需要的是：
Character lock system（角色锁定系统）
它的职责是保证：
父亲在 6 个分镜里是同一个人
女儿在 6 个分镜里是同一个人
不能一会戴眼镜一会不戴
不能从普通圆脸变成萌系二次元脸
不能从“怒气靠姿态”漂成“张嘴大吼”

4）分镜执行说明
你的 6 个分镜已经不是粗分镜，而是接近：
shot spec（镜头规格书）
每条已经含有：
镜头编号
时长建议
场景
角色
原文对应
景别
构图
动作
光线变化
情绪变化
镜头运动
视觉重点
所以这时“自动分镜 Agent”已经不是核心，核心是：
shot compiler（镜头编译器）
把每一条 shot spec 编译成适合图像模型 / 视频模型的执行输入。

所以，整套系统该怎么微调？

一、把“导演 Agent”改造成“双层结构”
我建议从单个“导演脑”改成两个 Agent：
A. Creative Interpreter（创意解释器）
职责不是创作，而是解析上游产线结果，抽出结构化字段：
global style
global negatives
story arc
character bible
prop bible
scene bible
shot list
emotional curve
lighting curve
continuity rules
它更像“编剧助理 + 制片统筹”。

B. Execution Director（执行导演）
职责是把结构化信息转成：
每个分镜的图像生成任务
每个分镜的视频生成任务
参考图依赖关系
首帧 / 尾帧 / 过渡帧策略
哪些镜头要固定机位，哪些要微推
哪些镜头应该继承前一镜的空间和姿态
它更像“执行导演 + 场记 + continuity supervisor”。

二、你原先最需要补的一层：结构化中间表示（IR）
这一步非常重要。
因为你上游给的是中文自然语言，非常强，但如果直接喂给模型，会出现两个问题：

七、你这个上游产线，还建议再补两类字段
你已经很强了，但我建议再加两个字段，会对自动化帮助特别大。

补充字段 1：镜头起止状态（start state / end state）
现在你的分镜主要是描述镜头内部内容，但视频生成尤其吃“起点”和“终点”。
比如分镜 06：
start：父亲僵住，手停在半空，红笔还在手里
end：红笔放回桌角，肩膀垮下，画面拉远，暖光完全漫开
如果你把这类字段显式写出来，
LTX / Wan / 混元这种首尾帧或图生视频流程会更稳定。

补充字段 2：优先保真项（priority locks）
每个镜头并不是所有信息都同样重要。
建议你给每镜加一个：
YAMLpriority_locks:  - father_identity  - daughter_identity  - red_pen_visibility  - bluegray_to_warm_transition  - whitespace_change
这样当模型能力不够时，系统知道先保什么，后牺牲什么。
这在自动重试时特别有用。
